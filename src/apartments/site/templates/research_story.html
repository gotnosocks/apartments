What a rent is made of

Why does one one-bedroom in {{ meta.scope }} ask far more than another a few blocks away? This page tells the story of the model behind this site: what it says an ask is built from, how sure it is, and what we learned building it. Every number here is read from the model now serving estimates, so the page changes when the model does.

The model has seen {{ "{:,}".format(counts[0]) }} asks for {{ "{:,}".format(counts[1]) }} apartments in {{ "{:,}".format(counts[2]) }} buildings, from {{ month(counts[3]) }} to {{ month(counts[4]) }}. Most apartments were listed more than once, so the same home shows up at different times and prices. That repetition is what lets a model separate the apartment from the building, and the building from the market.

An ask is a sum of a few stories

Start with the shape. The model writes the logarithm of each ask as a sum of parts, so each part works as a percentage: a building that is 10% pricier than its features explain adds 10% to every one of its apartments, whatever their size. Read the stack from the top. Each layer explains what the layers above it leave over.

What the features are worth

Inside the features layer, each detail of a listing has a price. The chart shows the details that move the typical ask by at least 2% and whose 95% interval doesn't cross zero. Each one is set against what a renter would compare it with: a studio against a one-bedroom, a newer building against one from the 1900s. A dot is the model's best estimate, and the line is the range it can't rule out. All else is held equal, so "two full baths" means two baths in an apartment that is otherwise the same, not the typical two-bath apartment, which is also bigger.

How close does it get?

The fairest test of an estimate is an ask the model never saw. The served fit left out {{ "{:,}".format(accuracy.n) }} asks (the held-out listings), and the site estimates each of them from the fit alone. Half of them land within {{ "{:.1f}".format(accuracy.median) }}% of their estimate.{% if accuracy.seen and accuracy.new %} It depends a lot on whether the model has seen the apartment before: for one listed at other times, half the asks land within {{ "{:.1f}".format(accuracy.seen.median) }}%; for the {{ "{:,}".format(accuracy.new.n) }} asks from apartments it has never seen, within {{ "{:.1f}".format(accuracy.new.median) }}%.{% endif %}

The model also says how sure it is. Each estimate carries a likely ask range, the middle 80% of the asks it expects for that apartment. If those ranges are honest, about 80% of the held-out asks should fall inside them; here {{ "{:.0f}".format(accuracy.likely) }}% do.

Theories on trial

A model like this is a pile of hypotheses. Does a quiet street cost more? Do bigger apartments' asks scatter more widely? Does the ad's own text know something the structured fields don't? Each idea gets the same trial. We fit the model with it and without it, on the same rows, and ask which version better predicts asks it was not shown. The score is PSIS-LOO, a fast stand-in for leaving each listing out in turn and predicting it from the rest. The score's unit is abstract; what matters is the difference between two fits (ΔELPD). Each difference comes with a standard error, a measure of how much it could move by chance, and a change counts as a real gain only when it beats the old model by more than twice that.

So far {{ trials | length }} ideas have been tried, in {{ tests | length }} paired fits. {% set others = trials | length - gains | length - nulls | length %}{{ gains | length }} helped, {{ nulls | length }} made no clear difference{% if others %} and {{ others }} made it worse or were set aside{% endif %}.{% if location %} The nulls tell a story of their own: {{ location_nulls | length }} of the {{ location | length }} ideas about where a building sits, from nearby subway lines to parks and street noise, changed nothing we could measure. The likely reason is that each building already has its own premium. Whatever a location is worth is already priced into that premium, so a new location feature has little left to explain. {% set waiting_now = location_nulls | selectattr("retest", "equalto", "next neighbourhood") | list %}{% if waiting_now %} {{ waiting_now | length }} of these nulls will be retested when a new neighbourhood joins the data, since more neighbourhoods give location more room to matter.{% endif %}{% endif %}

Cleaning the record

Before the model sees a single ask, the {{ "{:,}".format(cleaning.start.rows) }} rows pass through {{ cleaning.steps | length }} data rules. A listing site records the same apartment many times, from many brokers, over many years, and each rule fixes one way that record goes wrong.{% if cleaning.current and cleaning.end.rows > counts[0] %} Of the {{ "{:,}".format(cleaning.end.rows) }} rows that come out, the model is fitted on the {{ "{:,}".format(counts[0]) }} counted at the top of this page; the other {{ "{:,}".format(cleaning.end.rows - counts[0]) }} are held out to check its predictions on asks it hasn't seen.{% endif %}{% if not cleaning.current %} (These numbers are for the rules of an earlier served fit; they are refreshed when the rules change.){% endif %}

The rules that matter most are about identity. The model gives every apartment its own level, so it has to know which asks are the same apartment. Brokers spell unit names in different ways, "4-FLR" and "4FLR", "PH04" and "PH4", so {{ "{:,}".format(cleaning.joined) }} unit names were joined to the apartment they name. The opposite mistake happens too: one unit page can hold a one-bedroom and, years later, a combined four-bedroom. Where a unit's bedroom count changes from one ad to the next, its history is split there, and that made {{ "{:,}".format(cleaning.split) }} more units.

The other rules touch fewer rows. {{ "{:,}".format(cleaning.dropped) }} rows{% if cleaning.dropped_buildings %}, including every row of {{ cleaning.dropped_buildings }} buildings,{% endif %} were set aside after a review, for example ads that place the apartment somewhere else, offer a shop or a room, or contradict their own ask. {{ "{:,}".format(cleaning.corrected) }} bedroom and bath counts were corrected, but only where the ad's count is backed by at least half of the unit's other listings, when it has any. An ad's description never overrides its coded fields by itself.

Rules are tested like model terms: the model is fitted with and without the rule and scored on the rows both fits keep, the same trial as the ideas in Theories on trial. The data quality page lists every data rule and its reviews.
