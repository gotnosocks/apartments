# Inference prior art for the GPU-frontier model (2026-09-23)

Survey done before writing any inference code of my own. Versions were checked on
PyPI today and installed in a throwaway venv to read the actual APIs:
JAX 0.11.2, NumPyro 0.22.0, BlackJAX 1.6.2, PyMC 6.3.2, pymc-extras 0.15.1,
nutpie 0.16.11.

## The model class

Log asking rent = named feature terms + month trend + season + building effect
(optionally a building time walk) + unit effect + Student-t noise. This is a
*latent Gaussian model*: about 24k Gaussian latents (22k units, 1.1k buildings,
~300 global terms) and a handful of scale hyperparameters. Units nest inside
buildings. A sampler that exploits that structure can draw all latents jointly
at low cost. A generic gradient sampler has to fight the hierarchical funnels.

## What this repo already measured

From `docs/analysis/chelsea-sampler-reassessment-2026-09-18.md` and
`docs/analysis/modal-remote-fitting-2026-09-23.md`:

- nutpie/Numba on CPU is the working default: about 55 min per full fit, $0.38 on Modal.
- NumPyro NUTS (window adaptation) on GPU: correct in float64, but it needs
  6–10× more gradients per draw than nutpie and has ~30 ms single-chain
  gradient latency. It was slower overall. In float32 the chains did not move.
- The GPU gradient is cheap only when batched: 256 chains cost 0.010–0.025 ms
  per gradient per chain on A100/H100, against 2.6 ms for one CPU core. **Any
  GPU win has to come from many parallel chains or from structure, not from
  one faster chain.**

## Options found

| Option | What it is | Fit for this model |
|---|---|---|
| nutpie (PyMC) | NUTS, Stan-style or low-rank / normalizing-flow mass-matrix adaptation; Numba or JAX backend | Known quantity (55 min). Flow adaptation targets funnels, but a low-rank trial here was stopped for runtime and memory. |
| NumPyro `NUTS` | Standard NUTS; `LocScaleReparam` can learn how centered each effect should be | Correct, tested. CPU float64 has not been benchmarked here; GPU was slow. |
| BlackJAX `chees_adaptation`, `meads_adaptation` (+ low-rank), `adjusted_mclmc` | Adaptation built for **many chains in parallel** on accelerators (Hoffman & Sountsov); pairs with nested R-hat | The designed-for-GPU route, and not yet tried here. Risk: every chain must reach stationarity, so warmup dominates. |
| BlackJAX `window_adaptation_low_rank` | nutpie's Fisher-divergence low-rank metric, ported | A cheap variant to try alongside the above. |
| BlackJAX `laplace_hmc` / `laplace_dhmc` | HMC on hyperparameters, latents integrated by Laplace | Uses `jax.hessian` + dense `slogdet`. That is 24k² ≈ 4.6 GB per evaluation, so infeasible here as written. |
| pymc-extras `fit_INLA`, `marginalize(laplace_approx=…)` | INLA / Laplace marginalization | Explicitly experimental. Dense Hessian via `pytensor.gradient.hessian`, so the same size problem. |
| pymc-extras `marginalize` (exact Normal–Normal) | Closed-form marginalization of conjugate pairs | Would integrate unit effects exactly, but only with a Gaussian likelihood. The noise here is Student-t. |
| NumPyro `Gibbs` / `HMCGibbs` / `CustomGibbs` | Tested Gibbs combinator: NUTS on some sites, a user-supplied exact conditional on others | Lets the one structure-exploiting step (joint Gaussian draw of all latents given scales and Student-t weights) plug into a maintained MCMC driver, with its chains, `Predictive` and diagnostics. Only the conditional draw is custom. |
| BlackJAX `elliptical_slice`, `mgrad_gaussian` | Samplers for latent Gaussian models | Need a dense prior covariance (SVD / Cholesky of 24k×24k), so infeasible as written. |
| NumPyro SVI (`AutoNormal`, `AutoLowRankMultivariateNormal`), pymc-extras `fit_dadvi`, `fit_pathfinder` | Variational / Pathfinder | Fast, approximate. Suitable as a *screening* tier only if validated against an exact sampler on ΔELPD ranking. |
| R-INLA, lme4/glmmTMB/TMB, MCMCglmm | Mature sparse latent-Gaussian tools (sparse Cholesky / Laplace; block Gibbs) | No R on this machine. They are the canonical prior art for the structure; MCMCglmm-style block Gibbs is what NumPyro `Gibbs` + one conditional would reproduce. |
| Sparse Cholesky wheels | `cholespy` 2.2 (CPU/CUDA, DLPack to JAX), `pypardiso`, `qdldl` install as wheels; `scikit-sparse` needs a C compiler, which this machine lacks | Needed only if a design breaks the nested block structure (for example crossed effects). |

Relevant literature: Papaspiliopoulos, Roberts & Zanella (2020) on collapsed
Gibbs for crossed random effects; Rue, Martino & Chopin (2009) INLA;
Hoffman & Sountsov (2022) MEADS / ChEES and nested R-hat for many-chain GPU MCMC.

## Recommendation

1. Write the model **once**, as a NumPyro model: named additive terms, a
   Student-t likelihood, and a parameterization that can be centered or
   non-centered. All inference routes consume it.
2. **Baseline, exact, no custom inference:** NumPyro NUTS, CPU float64. It
   gives a correct reference and the whole data → score → leaderboard pipeline.
3. **GPU route, still library-only:** BlackJAX ChEES / MEADS / adjusted-MCLMC
   with 64–256 chains on a cheap Modal canary, judged by nested R-hat and
   ESS per dollar against (2).
4. **Only if (2)–(3) are too slow:** NumPyro `Gibbs` with one custom
   conditional, the structured joint Gaussian draw. It gets tested against a
   dense solve on a small synthetic problem. This is the one primitive worth
   writing, because no library exploits the unit-in-building nesting.
5. **Screening tier:** NumPyro SVI or DADVI, used only to rank candidates, and
   only after its ranking is checked against (2) on a few designs.

A draft of the custom joint-Gaussian Gibbs step was written before this review
and is parked, uncommitted, at `/data1/apartments/frontier/drafts/custom-gibbs-20260923/`.
It never ran on real data.
